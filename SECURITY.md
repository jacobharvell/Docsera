# Security policy

## Reporting a vulnerability

Do not report suspected vulnerabilities in public GitHub issues, pull requests, discussions, or comments. Do not include credentials, tokens, instance details, or proof-of-concept exploit details in public content.

GitHub private vulnerability reporting is available only after the repository is public. During final publication activation, the repository owner must make the repository public, immediately enable private vulnerability reporting, and verify that the repository's **Security** tab exposes the private reporting flow before announcing or promoting the release. Once that verification is complete, use that private reporting flow for security reports.

If that private-reporting option is not visible, do not post the vulnerability publicly. The repository owner must reverse public visibility until an approved alternative private disclosure channel exists; no private reporting route is promised before that activation is complete.

## Handling reports

Security reports should contain only the information needed to reproduce and assess the issue, shared through the private reporting flow. Please allow maintainers to investigate before public disclosure. This repository does not currently publish a response-time commitment, support SLA, or other contact channel.

## Scope

Use this policy for potential security weaknesses in Docsera source, packaged artifacts, or documented installation/deployment procedures. For ordinary installation questions, defects without a security impact, or feature proposals, follow [SUPPORT.md](SUPPORT.md).
