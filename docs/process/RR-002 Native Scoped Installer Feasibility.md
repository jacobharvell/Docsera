# RR-002 — Native Scoped Installer Feasibility

Date: 2026-10-30
Base examined: `origin/main` at `7b9a562b15358805b1ec7aa3364a09087ba6055d`
Status: investigation only. No export, install, PDI access, source-instance change, or release validation was performed.

## Decision

There is **no supported, consumer-grade, cross-organization native distribution path that meets the current GitHub-Release-only constraint**. The only ServiceNow-documented channel for sharing an application with all ServiceNow customers is the ServiceNow Store. That is expressly out of scope unless a new decision is made. Application Repository is limited to instances of the publisher's company; SDK installation requires a local source project and authenticated administrator/developer workflow. Neither meets the intended ordinary-administrator GitHub-download experience.

The most defensible next proof is therefore a deliberately bounded experiment of the platform's documented **Publish to Update Set** export capability—not a claim that an update set is a supported application installer. It may establish whether a complete, portable artifact can technically reach a clean unrelated instance. It cannot remove the product-policy conflict: ServiceNow's update-set planning guidance says not to use update sets to install applications and instead directs installation to Application Repository or Store.

Do not publish an installer claim, GitHub Release installation guide, or compatibility statement unless this experiment succeeds and Jacob explicitly accepts the remaining update-set-support limitation, or a new distribution decision authorizes Store publication.

## Official-service guidance reconciled

| Mechanism | What the documentation says | Fit for Docsera's requirement |
| --- | --- | --- |
| Publish scoped app to Update Set | Creates a complete update set from the current version's application configuration records; documentation says it can be transferred to another instance. Application sharing lists this as an export available to any instance with the file, normally for compliance/backup. | Technically plausible, but **not a supported normal installer recommendation**. Update-set planning explicitly says not to use update sets to install applications. Experiment only. |
| Application Repository | Installs/updates scoped apps entitled to the publisher's company instances. | Does not cross organizations. Reference only. |
| ServiceNow Store | Documented sharing channel for applications to all ServiceNow customers. | Supported cross-organization alternative, but outside the accepted distribution decision; requires a new decision and any applicable publisher/Store process. |
| SDK `build`/`pack`/`install` | Builds a local source project and installs it to an authenticated instance; `admin` is required. | Contributor/developer route only. It does not meet “ordinary administrator, no source/SDK.” Its ZIP format is not established here as a UI-importable cross-organization installer. |

The apparent conflict is resolved by treating the update-set publication feature as an export and transfer mechanism that must be proven technically, while respecting the later, explicit planning instruction that it is not the normal application-install channel. The capability does not make the path supported for Docsera's proposed public customer installation.

1. Jacob chooses a disposable but truly clean PDI on the target family and records URL, family/build, timestamp, installer identity, and that no Docsera metadata exists. Preserve the current development PDI and its evidence before any source-side action.
2. Freeze a named source commit/tag and exact component versions. Hash every candidate file (`SHA-256`) and make a release manifest containing source SHA, app version, scope ID, Global companion version/hash, target family, and expected inventory below.

### Install sequence

1. Record clean baseline searches/counts for the scope, all thirteen tables, `docsera` UI page, the scoped fallback page, REST definition/operations, roles, jobs, assets, ACLs, indexes, dictionary, and choices.
2. Import/retrieve the scoped exported artifact using the standard update-set UI. 5. Re-run complete inventory and functional smoke. Preserve retrieved-set logs, preview output, commit output, record exports/screenshots, HTTP/error logs available through normal administration, and the final file hashes.

### Installed-schema and enforcement protocol

Generated Fluent source, `keys.ts`, and a successful SDK build are only expected-state evidence. The clean target must establish installed behavior directly:

1. Export/list target `sys_db_object` records for the thirteen full table names and record `sys_id`, scope/package, label, active state, extension/super class, and table access attributes.
2. For every expected field, inspect installed `sys_dictionary` and `sys_documentation`: table/element, internal type, max length, mandatory/default/reference/choice/table attributes, active state, scope, and sys_id. Compare these normalized facts against the frozen source manifest, not filenames.
3. Inspect installed `sys_choice_set` and `sys_choice` by table/element. Record value, label, sequence, inactive/dependent/language fields, scope, and sys_id. Confirm the expected choice-set/choice counts after accounting for platform-generated rows.
4. Inspect `sys_index` plus its actual column relationship/definition records for each expected index. Record index name/sys_id, logical table, active/unique flag, ordered column list, and scope. Do not infer column membership from an index name.
5. Prove enforcement with disposable target data: create one valid parent/workspace context, then attempt a duplicate for **each required unique key** through the same normal API/record operation available to the candidate. Record the precise rejection and verify no second record exists. For the edit-lease last-seen index, establish presence and columns but do not falsely label it unique. Clean up only through an explicitly approved disposable-instance procedure; do not delete records in this investigation.
6. Verify the scoped-to-Global dependency from installed records: target scope IDs on `sys_scope_privilege`, restricted caller access, Global workers' references to the scoped tables/roles, and `docsera.do`'s import of the scoped asset. Then verify both host URLs, hard refresh, and a lazy editor chunk without development-instance URLs.

## Acceptance tests and stop conditions

Pass criteria for the experiment are complete inventory parity, no unexplained preview/commit skips or collisions, physical schema/index/choice proof, duplicate rejection for every unique constraint, deployed module resolution, both UI hosts/assets, all 34 REST operations registered and representative authorization/persistence workflows, scheduled jobs present, and successful scoped-to-Global bridge behavior. This would establish only a **tested technical transport candidate**.

Stop immediately and preserve evidence if any of the following occurs: a foreign identity/name collision; missing/incorrect scope; manual record creation or alteration becomes necessary; any expected table/module/asset/REST operation/role/ACL/job is absent; physical index/dictionary/choice mismatch; unique constraint fails; Global privilege or caller-access cannot resolve; preview/commit skips a required record; source/target family incompatibility; or target import changes unrelated records. Do not retry by changing source configuration during the same clean-instance run.

Even a pass remains blocked for public installer selection by the documented “do not use update sets to install applications” guidance. Jacob must decide whether to accept that limitation for a future proof-of-concept or reopen the distribution decision (Store is the documented cross-company path).

## Source export is not read-only

Publishing the scoped application to an update set is an operation on the source instance. The ServiceNow procedure asks for a Version and states that the platform saves it to the application **Version** field; it creates a complete update set and copies the latest application-file updates into it. It can also include limited sample data and transfer record-number counters when that option is selected. Therefore:

- Jacob must explicitly approve the source export and chosen version before it occurs.
- Use no sample data (`Include data` off) for this packaging proof.
- Before export, preserve screenshots/exports of the app record (including existing Version), current update-set/application state, active app file inventory, and a recovery note identifying how the newly created source update set will be retained rather than overwritten.
- Record exporter identity, source instance family/build, timestamp, app version before/after, generated update-set sys_id/name, and SHA-256 of the downloaded XML. Leave the source update set complete; do not reopen, manually merge, edit `sys_update_xml`, or back out Default.
- Treat a changed Version or created update-set/configuration record as a material source change requiring an approval record. Do not run it on the only valuable PDI until the preservation set is safely retained.

## Known blockers and follow-ups

4. Physical index/dictionary/choice behavior, UI-asset transport, module resolution, ACL behavior, lifecycle upgrade/uninstall, entitlement/licensing classification, and cross-organization support remain unproven.
5. No source- or target-instance operation is authorized by this report. RR-002 ends with independent review of this proof plan.
