## 3. Existing identity compatibility

The repository currently declares:

```json
{
  "scope": "x_82900_docsera",
  "scopeId": "6997f092c3fd8310c569bf0d0501314d"
}
```

That scope uses the prior PDI's `82900` company key. It is not an identity that
this PDI owns. The valid, available scope format for this instance is
`x_2300756_docsera` (17 characters, within the SDK's 18-character limit).
Its `scopeId` must be issued by the SDK/application bootstrap for this target;
it must not be guessed, copied from `6997f092c3fd8310c569bf0d0501314d`, or
manually invented.

SDK 4.8.1 supports the required future bootstrap path with an explicit alias:

```powershell
now-sdk init --appName Docsera --packageName docsera-direct-ui-page-runtime `
  --scopeName x_2300756_docsera --template partial.typescript.react `
  --auth docsera-dev468303
```

This command is documented here as a supported future creation path only. It
was **not** run: RR-058 does not authorize application creation or source
conversion.

## 4. Conversion is required

Because the company key differs, source conversion is required before a clean
SDK installation. There is no observed instance-specific obstacle to creating
the new identity: the PDI exposes its company code, accepts the secured alias,
has an administrator authentication context, and has no collision for the
valid proposed scope.

Do not manually edit a few application references and then install. A source
search finds the old scope in 88 tracked `app/` files. The conversion must
cover the scoped app's configuration and literals (table/role names, REST and
Direct UI Page paths, assets, modules, and client/server endpoints), as well
as the Global companion's workers, bridges, scoped privileges, host asset
paths, and update-set artifacts.

The scoped and Global `generated/keys.ts` files are generated identity
registries, not text templates. The new `scopeId` comes from the new SDK
bootstrap; replacement record identities must be regenerated by the supported
SDK flow and reviewed as generated metadata. They must not be search-replaced
or fabricated. The new scoped application must be established first; only then
can a regenerated/reviewed Global companion target it.

## 5. Recommended smallest next step

Create a dedicated conversion-tool task before application creation. The tool
should accept only:

1. the verified target company code (or a validated target scope derived from
   it);
2. a new SDK-scaffolded target `scopeId`;
3. an explicit confirmation that the source is the canonical
   `x_82900_docsera` identity.

It should deterministically transform the mechanically scoped source and
Global companion references, reset only the generated identity material that
the supported SDK must regenerate, run the existing key checks, and emit a
reviewable conversion manifest. It should refuse an occupied target scope,
missing/invalid company code, an unscaffolded `scopeId`, or deployment. The
separate follow-up must obtain approval before any first scoped installation
and before Global companion installation.
