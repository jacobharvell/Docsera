## Scope and method

Examined the accepted implementation plan and Task 138 baseline. Evidence below distinguishes executed local counts, code-proven repeated work, and unmeasured hypotheses. No browser, instance, database plan, network trace, or end-to-end timing was collected. Costs called dominant below are dominant *identified work*, not a measured share of latency.

A disposable Node 24 script stripped types from the actual `workspaceChangeSetDomain.ts` with `node:module.stripTypeScriptTypes`, executed it in a VM, and wrapped the three arrays' `find` methods to count predicate calls. ## Prioritized candidates

1. **Pending response construction:** on the server, within one loaded generation, compute the edit projection at most once when non-Removed titles need it and build request-local indexes for titles and category/entry lookups. First isolate title projection if that provides a smaller reviewable change; separately assess batched attribution with ACL behavior intact. High evidence and unfavorable P×N scaling; user impact depends on P and endpoint timing. Add regression coverage for mixed Added/Modified/Moved/Removed, ordering, missing/invalid references and authority/recovery; count projection work in a focused test. No client durable cache or new runtime module boundary is needed.
2. **Measure and narrow normal page-list/mutation payload and materialization:** compare network bytes, database time and server projection against client work before deciding whether a safely narrower projection is justified. Likely high reach but correctness/security and installed runtime risk are high; do not remove validation or full-state data on speculation.
3. **Tree descendant work:** if browser traces show scripting or rendering dominates navigation/filtering, compute per-render selection/filter results once while preserving tree interaction contract. Moderate evidence, moderate complexity; validate root-heavy and nested, collapsed/expanded, matching/nonmatching and drag interactions. Virtualization is not supported by this evidence.
4. **Member lookups and launcher capability evaluation:** investigate only if large member/workspace counts demonstrate user impact. Preserve authorization, search exclusion, total counts and last-admin safeguards; query count alone is not latency.
5. **Document conversion/autosave and publish/discard:** profile representative complex documents and pending sets first. Target only a demonstrated redundant pass; preserve editor fidelity and snapshot/transaction recovery. These have potentially high impact but weaker current evidence and higher regression risk.

The recommended first implementation boundary is candidate 1's request-local pending-row construction, subject to independent review and a live baseline. It is bounded to one server operation and has deterministic regression evidence; it does not presume this explains page creation or the 21-page observation.
