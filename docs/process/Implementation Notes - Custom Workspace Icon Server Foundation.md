# Implementation Notes - Custom Workspace Icon Server Foundation

Docsera custom workspace icons use `x_82900_docsera_workspace_icon_asset` as the ServiceNow attachment owner. The asset starts as `staged`, records the requesting user plus canonical persisted attachment metadata, and becomes `claimed` when workspace provisioning accepts the opaque asset key with the real provisioning request sys_id.

Uploads are accepted only through `/api/x_82900_docsera/docsera_runtime/workspaces/icons`. The server requires effective Docsera Admin before creating the asset or attachment, persists the original raster file first, reloads the persisted `sys_attachment`, passes that `sys_attachment` GlideRecord to the scoped `GlideSysAttachment#getContentBase64` boundary, and validates extension, MIME, signature, size, and dimensions from the persisted content. Missing attachment records, failed persisted-content reads, and invalid uploads delete both the attachment and the asset row for that upload attempt, leaving no usable staged asset.

Workspace creation accepts uploaded icons only by opaque asset key. The server verifies the staged asset belongs to the current user, has a matching attachment owned by the asset row, and is not already claimed. For uploaded-icon provisioning, the server prepares the request row without inserting it, reserves the final request `sys_id` with `GlideRecord#setNewGuidValue`, claims the asset against that future request id, writes the server-canonical uploaded icon key/path/label onto the request, and then inserts the request once as `requested`. If the claim or insert fails, the server restores the asset claim when needed and leaves no runnable partial provisioning request. The claim path uses a guarded persisted update and reload verification so duplicate attempts do not both succeed. Built-in icon workspace creation still inserts directly into the normal `requested` worker contract. The global provisioning worker finalizes the claimed asset against the new workspace before marking the request `succeeded`. If uploaded-icon finalization fails after workspace insertion, the worker rolls back the workspace and provisioned groups, restores the asset claim to `staged` when it still belongs to the failed request, and marks the request failed.

Uploaded icon validation is intentionally small and server-local. It reads only enough PNG, JPEG, and WebP structure to confirm declared type, extension, dimensions, square shape, minimum size, the 1 MB limit, and complete supported container structure. PNG validation walks chunks from first IHDR through IEND and requires IDAT. JPEG validation requires SOF metadata plus an actual scan before EOI. WebP validation walks RIFF chunks with padding, requires VP8/VP8L payload data, and requires VP8X dimensions to match the following image payload. It rejects structurally truncated PNG, JPEG, and WebP VP8/VP8L/VP8X files without adding an image decoder dependency or transforming image bytes.

Uploaded icon bytes are delivered only through `/api/x_82900_docsera/docsera_runtime/workspaces/icons/file?assetKey=...`. The endpoint streams the validated attachment only after resolving the claimed asset and confirming the current user can view the associated workspace. Raw `sys_attachment` URLs are not the product delivery contract.
