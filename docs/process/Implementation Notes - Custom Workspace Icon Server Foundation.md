# Implementation Notes - Custom Workspace Icon Server Foundation

Docsera custom workspace icons use `x_82900_docsera_workspace_icon_asset` as the ServiceNow attachment owner. The asset starts as `staged`, records the requesting user plus canonical persisted attachment metadata, and becomes `claimed` when workspace provisioning accepts the opaque asset key with the real provisioning request sys_id.

Uploads are accepted only through `/api/x_82900_docsera/docsera_runtime/workspaces/icons`. Creation-stage uploads require effective Docsera Admin before creating the asset or attachment. Settings-stage uploads pass the target `workspaceSysId` and require effective Workspace Admin or Docsera Admin capability for that workspace before creating the asset or attachment. The server persists the original raster file first, reloads the persisted `sys_attachment`, passes that `sys_attachment` GlideRecord to the scoped `GlideSysAttachment#getContentBase64` boundary, and validates extension, MIME, signature, size, and dimensions from the persisted content. Missing attachment records, failed persisted-content reads, and invalid uploads delete both the attachment and the asset row for that upload attempt, leaving no usable staged asset.

Workspace creation accepts uploaded icons only by opaque asset key. The server verifies the staged asset belongs to the current user, has a matching attachment owned by the asset row, and is not already claimed. For uploaded-icon provisioning, the server prepares the request row without inserting it, reserves the final request `sys_id` with `GlideRecord#setNewGuidValue`, claims the asset against that future request id, writes the server-canonical uploaded icon key/path/label onto the request, and then inserts the request once as `requested`. If the claim or insert fails, the server restores the asset claim when needed and leaves no runnable partial provisioning request. The claim path uses a guarded persisted update and reload verification so duplicate attempts do not both succeed. Built-in icon workspace creation still inserts directly into the normal `requested` worker contract. The global provisioning worker finalizes the claimed asset against the new workspace before marking the request `succeeded`. If uploaded-icon finalization fails after workspace insertion, the worker rolls back the workspace and provisioned groups, restores the asset claim to `staged` when it still belongs to the failed request, and marks the request failed.

Uploaded icon validation is intentionally small and server-local. It reads only enough PNG, JPEG, and WebP structure to confirm declared type, extension, dimensions, square shape, minimum size, the 1 MB limit, and complete supported container structure. PNG validation walks chunks from first IHDR through IEND and requires IDAT. JPEG validation requires SOF metadata plus an actual scan before EOI. WebP validation walks RIFF chunks with padding, requires VP8/VP8L payload data, and requires VP8X dimensions to match the following image payload. It rejects structurally truncated PNG, JPEG, and WebP VP8/VP8L/VP8X files without adding an image decoder dependency or transforming image bytes.

Uploaded icon bytes are delivered only through `/api/x_82900_docsera/docsera_runtime/workspaces/icons/file?assetKey=...`. The endpoint streams the validated attachment only after resolving the claimed asset and confirming the current user can view the associated workspace. Raw `sys_attachment` URLs are not the product delivery contract.

Client identity surfaces reserve the uploaded-icon badge dimensions immediately but leave the badge empty while the authenticated request and image decode are pending or fail. They never substitute a monogram or built-in artwork for an uploaded icon. A path-bound request lifecycle prevents a previous workspace image from rendering after a switch; completed blobs may be reused only in the current session for the same authenticated loader and asset path. The individual image fades in only after its load event, without gating workspace navigation or content rendering.

Workspace Settings recovered-preview reads use the same file endpoint with `preview=settings` and `workspaceSysId`. That path is intentionally narrower than the claimed-icon reader: it streams only `staged` assets bound to the target workspace, owned by the current staging user, with no provisioning request, valid attachment ownership/metadata, and current Workspace Admin or Docsera Admin capability. Creation-stage assets with no target workspace remain unavailable through this preview path.

Abandoned settings-staged uploads are retired through `POST /api/x_82900_docsera/docsera_runtime/workspaces/icons?action=cleanup-settings-staged&assetKey=...&workspaceSysId=...`. Cleanup is best effort and guarded by target workspace, current staging user, `staged` state, and empty provisioning request. It cannot delete the currently authoritative claimed uploaded icon.

Claimed-icon retirement happens only after the authoritative Workspace Settings save has selected its replacement. On every later successful, authorized settings save, the server examines at most ten claimed assets for that workspace so an interrupted prior cleanup can be retried without background infrastructure. Before deleting anything, it verifies the claimed state, workspace association, attachment ownership, and the latest persisted workspace icon. A claim with no provisioning request is eligible; a creation-stage claim with a provisioning request is eligible only when that exact request is authoritatively `succeeded`, points to the same workspace, and records the same uploaded icon key. Requested, processing, failed, missing, or mismatched claims remain protected. The active uploaded icon, another workspace's asset, staged uploads, and invalid attachment associations are also left intact. The attachment is deleted first and reread from `sys_attachment`; only confirmed absence (including an attachment already absent from an earlier interrupted cleanup) permits a guarded deletion of the matching asset row. Each candidate is isolated during the bounded scan, so a throw or retained attachment leaves that asset durable for a later retry without blocking other eligible records. Cleanup remains best effort and cannot make the successful Settings save fail.
# Abandoned staged-upload retention

The SDK-managed `Docsera Abandoned Workspace Icon Cleanup` scheduled script runs daily. It processes at most 50 eligible assets per run: durable `cleaning` claims are retried first regardless of age, then staged uploads older than seven days from `sys_updated_on` fill any remaining capacity. The guarded staged-to-cleaning transition repeats the persisted retention-cutoff predicate, so an upload refreshed after selection remains staged. This includes creation-stage, Settings-stage, and failed-provisioning uploads restored to `staged`.

Cleanup changes an eligible asset from `staged` to durable `cleaning` with a guarded update. `cleaning` blocks workspace/provisioning claims and is retried after an interruption without restarting the retention window. Each attempt reloads the asset, excludes provisioning-linked assets, confirms that the attachment belongs to that exact icon-asset record, deletes the attachment first, confirms it is absent, then guarded-deletes the `cleaning` asset. Attachment failures, ownership mismatches, and interrupted jobs leave the durable record for a later run. The Settings best-effort endpoint follows the same attachment-first transition while retaining its existing owner and Workspace Admin checks.

Installation requires the scheduled-script and `cleaning` choice metadata to be included in the SDK package; no instance-side manual cleanup job is required.
